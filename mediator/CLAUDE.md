# CLAUDE.md

## Commands
- Part of the estoc pnpm workspace: `pnpm install` at the root, one lockfile there; `@estoc/did-peer` is `workspace:^` and resolves to its `dist/`, so build it (`pnpm --filter @estoc/did-peer run build`) before typechecking, testing or bundling here
- `pnpm test` — vitest; `pnpm run typecheck` — tsc for both targets (main config excludes `src/workers`; `tsconfig.workers.json` checks it with workerd types)
- `MEDIATOR_PUBLIC_URL=http://localhost:8080 pnpm run dev:node` — Node dev server (not `dev`: the root `pnpm dev` runs every package's `dev`, and this one needs a URL) (identity `did:web:localhost%3A8080`, same default as Workers; `MEDIATOR_DID_METHODS=peer2` for the offline-resolvable method)
- `pnpm run dev:workers` — wrangler dev, zero setup: keys are minted into the local D1 on first request, identity is `did:web:localhost%3A8787` (the resolver has a loopback-http fallback for exactly this)
- `pnpm run smoke <url>` — full client flow against any *running* mediator (grant → keylist → anonymous forward → pickup → WS live delivery with binary-frame asserts → blob put/upload/Range/renew/delete when advertised); the deploy verification tool
- `docker compose up -d` — production shape (needs `MEDIATOR_PUBLIC_URL`); the build context is the workspace root (`docker build -f mediator/Dockerfile .`), narrowed by `Dockerfile.dockerignore` to this directory and `packages/did-peer`
- `pnpm run deploy --env prod` — the production Worker; wrangler builds the workspace library first (`build.command`)

## Architecture
- **Hono + TypeScript ESM**, two deploy targets off one protocol layer. `src/app.ts` is the shared wire surface (POST `/` return-route, `/invitation`, `/health`, CORS; no `/.well-known/did` — that was an Affinidi convention, dropped in favor of OOB + plain GET `/`; a did:web identity *does* serve the standard `/.well-known/did.json` + `/did.json`, which is a different, spec-defined thing); its plain GET `/` steps aside on an Upgrade header so each target mounts its own WebSocket handler after it, answers browsers (Accept: text/html) with the human-readable invitation page, JSON otherwise. @estoc/didcomm-node (WASM build of the estoc-net/didcomm-rust fork — it refuses an attachment holding more than one of json/base64/links, which upstream silently reduces to one) does all crypto; the full pack/unpack API is what makes every enc-alg work without the hand-rolled envelope bugs the Affinidi fork had to patch
- **Node target** (`src/server.ts` + `src/index.ts`): @hono/node-server + @hono/node-ws, sessions in process memory (`src/transport/sessions.ts`), SQLite via better-sqlite3
- **Workers target** (`src/workers/`): same app, but **URL-agnostic and one app per origin** — no public URL is configured; `index.ts` keys a `Map<origin, Promise<Hono>>` off each request's origin and `depsForOrigin` derives that origin's identity (default method `web`, so workers.dev and any custom domain are simultaneously live DIDs of one mediator; a rejected build is evicted so a D1 hiccup can't poison an origin). D1Store (lazy CREATE TABLE, no migrations step); live sockets live in one `InboxHub` Durable Object (`idFromName("hub")`) with hibernatable WebSockets — DID + liveDelivery + **origin** ride each socket's serialized attachment (the DO resolves per-origin deps lazily and needs the origin after hibernation, when there is no request to read it from; an attachment without one gets closed with "reconnect"). The stateless Worker reaches it through the `LiveSink` interface (`wantsPush`/`push`); on Node the in-memory `Sessions` implements the same interface
- **didcomm on workerd** (`src/workers/didcomm-wasm.ts`): wrangler `alias` maps `@estoc/didcomm-node` → a shim that instantiates the `@estoc/didcomm` bundler build manually (`new WebAssembly.Instance(mod, { "./index_bg.js": glue })` + `__wbg_set_wasm` + `__wbindgen_start()`); identical API, same wasm. `nodejs_compat` supplies Buffer/node:crypto to shared code
- **Store** (`src/store/types.ts`): all methods async — D1 has no sync API and the protocol layer is shared. **One store implementation, `src/store/sql-store.ts` (`SqlStore`)**: better-sqlite3 and D1 are both SQLite, so schema + every query are written once against the narrowest shared contract — `SqlDriver.batch(statements)`, a list of statements run in order as ONE transaction (D1's only transaction shape; every transactional path fits it). Backends are thin drivers: `BetterSqliteDriver` (src/store/sqlite.ts, `SqliteStore` subclass) and `D1Driver` (src/workers/d1-store.ts, `D1Store` subclass). Schema is ensured lazily on first use (retry on failure). Tables: accounts (row = grant) / replica_accounts + replicas + replica_recipients (replica-mediation, below) / keylist (recipient_did PK → owner, exclusive first-come) / messages (TTL + per-account quota) / replica_packages + replica_deliveries (replica-mediation mail) / blobs + blob_uploads (blob-store, below) / identity (single row, the mediator's keys as JSON — `initIdentity` is INSERT OR IGNORE + re-read, so concurrent first mints all converge on the winner). Who is asking is proven in the protocol layer; that a DID is bound once, under one protocol, is kept inside the store's writing statements. (Long-lived databases may still carry `pf_*` tables from the removed public-folder relay; the code ignores them)
- `src/didcomm/` is copied lineage from `../didcomm-http` (did-peer-2/4, did-doc, did-resolver); keep fixes in sync. `src/identity-core.ts` is *all* of identity and fully runtime-free: **what is stored is two keys, nothing else** — no DID and no URL is ever persisted (`loadOrCreateSecrets(store)` load-or-mints the store's identity row; `mintSecrets` is WebCrypto, so the same code runs on Node and workerd; `identityFor(secrets, url, methods)` expands to every active name). **One key set, several simultaneous DIDs**: every method's DID derives deterministically from keys + URL, so which are active is config, not storage — `MEDIATOR_DID_METHODS`, ordered ("peer2,web"; first = primary/advertised, rest = aliases; unset means web on both targets — set peer2 for a non-loopback http URL). The peer2 encoding in identity-core is an **invariant**: every boot re-derives deployed DIDs from the keys, so changing it silently renames mediators. All methods share `#key-1` = X25519/keyAgreement, `#key-2` = Ed25519/authentication; secrets are absolutized once per active DID. Dispatch replies *as the DID the envelope addressed* (`ctx.asOwnDid(unpacked.addressedTo)`) — mediate-grant's routing_did and live-delivery pushes use it too. did:web requires an https public URL (resolvers only fetch https; loopback http is allowed for wrangler dev, with a matching fetch fallback in did-resolver), builds its own document from the stored keys — never fetched, the DIDCommContext pins all own docs — and publishes it at the did.json routes
- **Dispatch** (`src/protocols/dispatch.ts`): handlers return `{type, body, attachments?}`; dispatch alone fills id/thid/from/to and packs — replies are sealed to `verifiedFrom` (the DID the envelope proved), never `message.from`. Anonymous senders: `forward` only; unknown types get a problem-report only when there is a proven sender. **return_route is enforced strictly**: a reply is delivered on the inbound connection only if the message carries `return_route: "all"` (HTTP: every POST; WS: once marks `session.returnRoute` for the socket's lifetime, persisted in the DO attachment) — without it the handler still runs but the reply is dropped
- **Squat resistance**: recipient-update add refuses non-DIDs, >2048 chars, any of the mediator's own DIDs (plus the short form of a long-form did:peer:4), and DIDs holding their own account; forward prefers a local account over any binding **unconditionally** — test "delivers to a registered account DID over any squatted binding" pins this
- **Forward** (`src/protocols/routing.ts`; the contract is the README's "What a forward must be"): syntactic checks only, the inner envelope is never opened — the envelope is read from `Unpacked.plaintext` (the sender's JSON text, which `@estoc/didcomm` ≥ 0.4.1-estoc.4 returns as the third element of `Message.unpack`), never from the library's parsed `message`, which has already folded repeated member names and moved decimals; `parseUnambiguous` (momoa AST) refuses a repeated member name anywhere in the forward or in a decoded `base64` carrier, so both carriers give the same value; General JWE JSON shape (`isEncryptedMessage`: unpadded-base64url binary members, recipients with `header.kid` + `encrypted_key`, `protected` decoded by jose and, per recipient, `isJoseHeader`: protected / shared / per-recipient header names disjoint, `alg` + `enc` non-empty strings, `epk` / `apu` / `apv` / `skid` typed when present, algorithm names never judged; unknown members kept, numbers included); what is stored and handed over is `canonicalize(envelope)` (RFC 8785). A refusal is a thrown `ForwardRefused` that `app.ts` turns into the HTTP status (400 malformed; 413 when the canonical form exceeds `maxMessageBytes`, which a number like `1e20` can do under the wire ceiling; 422 for everything account-dependent — unknown `next`, full queue, key conflict — one answer on purpose); a 2xx always means queued. `messages` rows carry `(owner_did, next_did, forward_id)` under a unique index: same key + same bytes = accepted, nothing written, no second push; same key + other bytes = refused, first stays. The answer is the queue's: a live-delivery push that fails after the insert is noted through `HandlerContext.log` (passed by all three entries: `app.ts`, `server.ts`, `workers/inbox-hub.ts`) and the forward is still accepted. `storeMessage` is one batch (drop an expired holder of the key → quota-guarded `INSERT … ON CONFLICT DO NOTHING` → read the holder back; the fresh row id tells stored from repeated). A database from before the key gains the two nullable columns by `ALTER TABLE` on first use (`keyMessages`); its waiting rows keep NULLs, which a unique index never collides
- **Library errors never leave `src/didcomm/didcomm.ts`**: `unpack`/`packEncrypted` rethrow as `DIDCommFailure` (operation + the library's error kind, no message, no cause) — the library quotes what it was parsing, including headers of an envelope it already decrypted, and every transport logs what it catches
- **Pickup**: one inbox per ordinary account; `recipient_did` echoed, never used to scope (replicas: see replica-mediation below). Delivery attachments are **base64url**. Live delivery: WS session binds to first proven DID and never re-binds; push leaves messages queued until messages-received
- **blob-store/1.0** (`src/protocols/blob-store.ts` + `src/blobs/`; spec is `../docs/blob-store.md`): an agent holding a mediation `put`s `{hash, size}` (hash = sha-256 multihash, base32 lower `b…`, `src/blobs/hash.ts`, on `multiformats`) and gets `put-result {url, retain_until, upload?}`. **A blob is one mediation's**: the row is (owner_did, hash) unique, served at `/b/<id>` where the id is 20 random bytes base32 (`mintBlobId`) — the URL says nothing about the hash or the owner, and the same hash put by two mediations is two rows, two ids, two uploads (no sharing, no dedup; `delete` is final: row and bytes go at once). `upload.url` is `PUT /b/<id>?token=<one-time uuid>` **through the mediator itself** (not a presigned S3 URL — that would make every deployer set up object-storage account credentials; cost: Workers body limit, so `MEDIATOR_BLOB_MAX_BYTES` defaults to 100 MiB). `BlobStorage` (fs on Node, R2 with the `sha256` put option on Workers) keys bytes by id and is the only place they meet their hash; the DB holds `blobs` (id PK, owner_did — deliberately no FK so purge can still learn the id after the account goes —, hash, size, uploaded_at, retain_until; quota = SUM(size) of live rows; a repeat `put` extends retention, never shortens; `keepBlob` is one batch whose insert and renewal both carry the quota condition, so two puts cannot both pass a check neither has written for, a live blob renews for nothing and one past its retention is counted in full again; the row read back names `kept` / `mismatch` / `full`) / `blob_uploads` (tokens, consumed on claim). GET/HEAD `/b/<id>` with Range to anyone, 404 unless uploaded and still retained. Purge (cron on Workers, the hourly interval on Node) drops rows past retention or whose account is gone, then their bytes. A database still carrying the first schema (hash PK + `blob_holds`, 2026-08-26/27) is reset on first use — `dropOldBlobTables` — its bytes in storage (files/R2 objects named by hash) are the operator's to sweep. Off when `blobDir` is null / no `BLOBS` R2 binding: routes absent, protocol not advertised, `put` → `e.p.blob.refused`. `BlobService` rides `HandlerContext.blobs`; `GET /` advertises `blobs: {retainSeconds, maxBytes, quotaBytes}`
- **replica-mediation/1.0** (`src/protocols/replica-mediation.ts` + `replica-grant.ts`; the contract is the README's "Replica mediation" section plus the body types in the handler file, and nothing here depends on a document outside this directory; off unless `MEDIATOR_REPLICA_MEDIATION=true`, and then also advertised): accounts, `register`, `list`, `remove`, `recipient-update`, `recipient-query`, fan-out and replica pickup; the handler table is `REPLICA_CONTROLS` in the handler file. An account is a did:peer:4 that authcrypts `register` with a grant its own authentication key signed (compact JWS, jose `compactVerify` with the key taken from the account's document; payload must be its own RFC 8785 text with exactly the six fields); the request creates the account and its first replica in one batch or neither (`registerReplica`: the account insert carries every condition the replica insert has, then the rows read back name the outcome). **An account is bound to the one mediator DID its first grant named** (did:peer:4 compared in short form, both in the grant and in the replica's service URI; another name of the same deployment is another mediator: `register` → `identity-conflict`, `list` → `unknown-account`). A replica's document must carry Ed25519 authentication keys and X25519 key-agreement keys (`holdsKeys`, key bytes checked by jose `importJWK`). Replies to these controls use the request's `id` as `thid` even when the request carried a `thid` (decided in `dispatch.ts`). `replicaPolicyFrom` throws on a limit that is not a positive integer, and the account insert also requires room for one replica. Tables `replica_accounts` (did = short form, mediation_id, mediator, long_form) / `replicas` (replica_did PK, per-account unique replica_id and ordinal, long_form, grant_jws, registered_at in seconds); no row of either is ever deleted. **`remove`** (`removeReplica`, one batch) sets `replicas.removed_at` (seconds; NULL = active; added in place on an older database by `LATER_COLUMNS`), deletes that replica's deliveries and the packages forwarded to its own DID, and answers a repeat with the first time; a removed replica keeps its ordinal, ID and DID bound (`register` → `identity-conflict`), stops counting against `maxActiveReplicas` (the ordinal counts all rows, the limit only active ones), is no fan-out target, and is listed with `state: "removed"`; `replicaState` tells pickup, which answers a removed replica `replica-removed`. **A DID is replica-mediation's or ordinary mediation's, never both**, enforced inside the writing statements in both directions and across both spellings of a did:peer:4 (`spellings`, `NOT_ORDINARY`, `NOT_REPLICA_MEDIATION`): `grantMediation` returns false (mediate-deny), `addRecipient` returns `taken`, `registerReplica` returns `conflict`. **`recipient-update`** takes coordinate-mediation's shape under this protocol's own type: body exactly `updates`, 1 to `RECIPIENT_UPDATE_LIMIT` entries each exactly an addition or a removal (anything else refuses the whole request, `updatesOf`), applied in order, one store batch each, and answered per entry with `result` and, when refused, `problem`. An `add` entry (`recipient-proof.ts`) binds one did:peer:4 communication DID to the account: exactly `recipient_did`, `action`, `resolution_material`, `proof`; the proof is a compact JWS (`typ: estoc/recipient-add+jws`, same `signedPayload` verification as the grant) signed by the *recipient's* authentication key over exactly `{account, aud, recipient}`, each compared in short form against the request's sender, addressed mediator and named recipient, and checked on every request, a repeat included. `resolution_material` is the long form, or null once `replica_recipients` (recipient_did PK = short form, account_did, long_form) keeps one; that material is deliberately not part of `resolutionMaterial`, so a shared recipient does not become a sender the mediator resolves by short form. `addSharedRecipient` is one batch: the insert carries the account-at-this-mediator, unbound-everywhere and under-`MEDIATOR_MAX_SHARED_RECIPIENTS` conditions, and the owner read before and after tells `added` from `no_change` (an existing binding answers `no_change` even at the limit); a DID bound otherwise is `identity-conflict`, and `NOT_REPLICA_MEDIATION` now also keeps a shared recipient out of ordinary accounts, keylists, replicas and accounts. A `remove` entry (`removeSharedRecipient`) deletes the binding row, long form included, and nothing else: packages already kept for the DID keep their deliveries, and the DID is free for any binding, so `UNIQUE (next_did, forward_id)` outlives a move to another account (a forward repeated across the move is still a repeat). `recipient-query` (`listSharedRecipients`) is offset-paged, limit at most `maxMembershipPage`. Short-form senders resolve because `DIDCommContext` takes `resolutionMaterial` (the store's kept long forms), so first contact must use the long form and later requests need not. `list` cursors are `[account, through, after]` in base64url: the roster only appends, so "the first `through` replicas" is a snapshot that never expires. Account DIDs asking for pickup get `e.estoc.replica-mediation.replica-required`. **Fan-out** (`fanOut` in the store, reached from `routing.ts` only after no ordinary owner was found and only with the flag on): `next` in its short form is looked up among `replica_recipients` (shared: one delivery per active replica the account holds in that transaction) and `replicas` (private: one delivery, that replica's). One batch: drop a lapsed holder of the key → insert into `replica_packages` (id, account_did, next_did, forward_id, packed, bytes, created_at, expires_at; `UNIQUE (next_did, forward_id)`, store-wide, a recipient having one account at a time) only under the account's unexpired count (`maxMessagesPerAccount`) and byte sum (`MEDIATOR_MAX_RETAINED_BYTES`) → insert `replica_deliveries` (id = `lower(hex(randomblob(16)))`, package_id, replica_did) only if that package row exists → read the key's holder back. Registration is one batch too, so the two are serialized: a replica enrolled later is never a target, and a repeat writes nothing. `expires_at` is the earlier of now + `messageTtlSeconds` and the forward's `expires_time` (a past one is refused; ordinary queues ignore the header). Every refusal is the same 422 as an unknown `next`. `purgeExpired` drops lapsed packages with their deliveries. **Replica pickup** (`pickup.ts`, `inboxOf`): the queue a pickup request reads follows from the proven sender in its short form — a replica-mediation account gets `replica-required`, a replica gets its deliveries (`deliveriesFor` / `deliveryCount`, where `recipient_did` in its short form narrows to `replica_packages.next_did`; ordinary inboxes still only echo it), an ordinary account its inbox, anyone else silence; a replica's request must be authcrypt (`isAuthcrypted`, the same test the controls use: `verifiedFrom` alone also accepts a signature) or it is met with silence too; on a WebSocket, pickup from a DID other than the one the session is bound to gets `e.p.msg.connection-bound` before anything is read or changed, both spellings of the bound did:peer:4 being the same DID; this is not behind the flag, so a deployment that turned it off still drains. Attachment ids are delivery ids, one per (package, replica). `acknowledgeDeliveries` is one batch: delete the named deliveries that are this replica's (`id IN (SELECT value FROM json_each(?))`, one statement whatever the list's length; other ids match nothing), then delete packages forwarded to this replica that have no delivery left — a private package has exactly one, so that is the acknowledged ones; a shared package stays until it expires, for the other replicas and for repeat detection. A stored fan-out returns its deliveries and `routing.ts` offers each to its replica's live sessions (`offer`), failures noted and the forward still accepted. `Sessions` indexes a did:peer:4 under its short form on bind and on lookup, because a socket proves whichever spelling it sealed with while pushes go to the spelling the store keeps (and are sealed to it: a replica must hold its keys under the short form's ids to open a push)
- **OOB invitation** (`src/oob.ts`): out-of-band/2.0 invitation, deterministic id (sha256 of DID) so the QR/URL never changes across boots; `?_oob=` base64url on the public URL, plaintext JWM at `GET /invitation`. Issue-only — no inbound handler, invitations travel as URLs not envelopes; deliberately **not** in `SUPPORTED_PROTOCOLS` (that list doubles as the discover-features disclosure of what you can *send* us)

## Gotchas
- **WS frames are sent as text, received as either**: the DIDComm v2 spec never specifies the frame type, so implementations disagree — Credo sends binary, ACA-Py accepts both. Text frames arrive as plain strings in every environment (browser/RN/Node) while binary arrives as Blob/Buffer/ArrayBuffer, so we send text and tolerate both inbound. Headless ws clients mask frame-type bugs; the demo-interop test and smoke assert `isBinary === false`
- the fork's `new Message()` refuses what the mediator must refuse (multi-carrier attachment data), so tests for those build the JWE by hand — `sealRaw` in `test/helpers.ts` (jose)
- didcomm-node needs `message.from` to match the packing key: test helpers must set `from`/`to` in the plaintext
- didcomm-rust re-serializes JSON with sorted keys — compare forwarded payloads structurally, never by string equality
- `pack_encrypted` here always `forward: false` — the mediator replies directly; wrapping its own replies for another mediator would be wrong
- vitest runs HTTP tests via Hono's `app.request()`, but live delivery needs a real listen + `ws` client (`test/live-delivery.test.ts`)
- tsconfig `rootDir: "src"` and `exclude: src/workers` so Docker's `tsc` emits `dist/index.js` without workerd types
- The `@hono/node-server` audit advisory (serve-static path traversal on Windows) doesn't apply: nothing is served statically
